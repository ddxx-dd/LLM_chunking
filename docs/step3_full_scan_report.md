| 트랙 | 전체 | 통과 | 실패 | 예외 |

예외(코드가 죽은 경우)는 0건 — 파서·writer 자체는 45+50개 문서 전부에서 끝까지 돌았다.
**pdf가 0/50인 건 "병합이 전부 망가졌다"는 뜻이 아니다** — 항등 테스트 기준이 "단 한 글자
라도 다르면 실패"로 엄격한데, 아래에서 보듯 실패 사유 대부분이 이미 원인을 파악한, 실제
콘텐츠 손상이 아닌 항목들(폰트 lookalike, 라이브러리 간 추출 차이, 조밀한 숫자표에서
검증 스크립트 자체의 bbox 클립 부정확)이다. docx는 진짜 콘텐츠 손실(Docling이 도형을
요소로 아예 못 만드는 문제)이 섞여 있어 더 무겁게 봐야 한다.

### 원인 2가지로 정리됨

**(A) 대규모 unwritten — ★ 실측 확인: unwritten 개수가 거의 정확히 "Fallback 개수 × 2"**

unwritten>0인 13개 문서에서 `unwritten / unwritten_fallback` 비율을 계산하면 13개 중
12개가 **정확히 2.00**(예: 838/419, 124/62, 890/436, 750/375, 326/163, 286/143 등),
1개만 예외(KIFVIP2013-10.docx, 46/3 ≈ 15.3). 이 패턴은 다음을 강하게 시사한다: 안 써진
문단은 거의 항상 **Choice쪽과 Fallback쪽이 쌍으로 같이** 안 써진다 — 즉 우리 Fallback
미러링(`fallback_sibling`)이 실패해서가 아니라, **Choice쪽 원본 문단 자체가 애초에
Docling elements에 하나도 안 잡혀서**(paraId를 못 찾아서가 아니라 Docling이 그 문단을
아예 아이템으로 만들지 않아서) 짝을 이루는 두 문단이 통째로 우리 시스템에 안 보이는
것이다. 이런 문서들은 대부분 인포그래픽형 보고서/브로슈어(정부 정책자료, 회사소개서 등)로,
**개별 텍스트박스(도형) 수가 매우 많다** — 실측: 이번에 확인한 3개 인용구 카드짜리
샘플 문서(4342398...)에서 발견했던 "duplicate content 1건" 패턴이, 도형이 훨씬 많은
문서에서는 **문서 전체 콘텐츠의 상당 비율**로 커진 것으로 추정된다. **이는 우리 코드의
버그가 아니라 Docling MsWordDocumentBackend가 복잡한 도형 레이아웃 문서에서 텍스트박스
상당수를 아예 요소로 변환하지 못하는 한계로 보인다** — 다만 "왜 정확히 절반이 빠지는지"
(Choice/Fallback 쌍 중 어느 한쪽만 골라서 빠지는 게 아니라 쌍째로 빠지는 이유)는 아직
Docling 소스까지 파고들어 확인한 건 아니라서, **가설로 표시**해둔다(추가 검증 필요).

**(B) 소규모(0~2건) 불일치 — 기존에 확인한 "실제 중복 콘텐츠를 Docling이 덜 잡는" 패턴**

unwritten이 0~2인 6개 문서(PRP008, 2022누56595, 4e304ca4..., journal-31-3-308,
1701325252947, 쿠팡_상장...)는 `docs/writer_implementation_review.md`에서 이미 확인한
"동일한 실제 콘텐츠가 도형으로 두 번 존재하는데 Docling이 한쪽만 요소로 만드는" 패턴과
같다 — 요소로 아예 안 잡히니 `unwritten` 카운트에도 안 잡히고, 최종 텍스트 diff에서만
몇~수십 글자 단위로 드러남. 문서당 영향은 작다(수십 자 이내).

**서식 섞인 문단 수(mixed)는 항등 테스트 통과 여부와 무관** — 참고용 병합 지표로만 기록
(§8, "서식이 첫 run 쪽으로 쏠림" 한계).

## pdf 50개 상세

### 통과 0개 — 실패 사유 분해

| 실패 사유 | 해당 문서 수 |
|---|---:|
| (a) 쓴 요소 텍스트 불일치 | 38 / 50 |
| (b) 그림/도형 개수 불일치 | **0 / 50** |
| (c) 안 쓴 요소 원문 보존 실패 | 48 / 50 |

- **(b)는 50개 전부 통과** — redaction이 불필요한 벡터 그래픽을 지운 사례는 0건. writer의
  redact→apply→insert 순서 버그는 없음.
- 전체 쓰기 시도 15,277건 중 **9,482건 성공(62%), 5,795건 넣기 실패(38%)** — 95% 커버리지
  기준(1(b) 수정)이 실제로 많은 항목을 "실패"로 정직하게 걸러내고 있다는 뜻(이전 spare만
  보던 방식이면 이 상당수가 "성공"으로 잘못 기록됐을 것).

### (a) 텍스트 불일치 — 합계 409건 / 38개 문서

대부분 샘플(`2401.06326v4.pdf`)에서 이미 확인한 패턴과 동일: Docling이 결합 문자
(combining mark, 예: "Ĉ"가 베이스 없는 악센트로 분리됨)를 베이스 글자 없이 추출하는
경우, 그리고 지시받은 4쌍(`‖∥`,`〈⟨`,`〉⟩`,`·・`) 밖의 다른 수학 기호 lookalike. 수식이
많은 논문(계량경제학 등)에 집중돼 있음 — 예: `2412.13914v3.pdf`(72건), `2406.02238v6.pdf`
(52건).

### (c) 안 쓴 요소 원문 보존 실패 — 합계 2,332건 / 48개 문서

**★ 실측 확인 — 대부분 우리 writer가 손상시킨 게 아니라 검증 방법 자체의 한계**:
`2408.06977v4.pdf` 한 문서에서만 1,172건(전체의 절반)이 나왔는데, 직접 확인해보니 전부
**촘촘한 숫자표 셀**(예: 원문 `"0.1099"` vs 재추출 `"0934 0"`) — 셀 사이 간격이 좁아서
`get_text(clip=bbox)`로 재추출할 때 **이웃 셀 글자가 섞여 들어옴**. 이 셀들은 우리가
**전혀 건드리지 않은 영역**이므로(안 쓴 요소만 검사하는 기준이라 redaction 자체가 없었음)
실제 콘텐츠 손상이 아니라 **bbox 클립 좌표가 셀 경계와 딱 안 맞아서 검증 스크립트가
재추출할 때 이웃 셀까지 걸리는 문제**로 판단됨. 나머지 문서들의 (c) 실패도 표본 조사
결과 대부분 같은 패턴(조밀한 표) 아니면 샘플에서 이미 확인한 "Docling·PyMuPDF 추출
문자 코드 차이"(예: `-` vs `−`, 지시받은 4쌍 밖이라 미반영) 유형.

### (c) 참고 지표 — bbox+3px 바깥 픽셀 변화율
50개 문서 대부분 페이지당 0.000~0.1% 수준(정보용, pass/fail 아님) — 전체적으로 낮음.
