## 3. 단순 글자수 분할

### 알고리즘

오프셋 슬라이싱. `text[start : start + chunk_size]`를
`step = chunk_size - overlap`만큼 전진하며 반복한다.
문장 경계를 고려하지 않는다.

### 결과 (부산행.srt, chunk_size=512, overlap=0)

원본 9,345글자 / 6,767토큰

| 지표 | 값 |
|---|---|
| 청크 수 | 19 |
| 평균 글자 | 491.8 |
| 평균 토큰 | 356.5 |
| 최소/최대 토큰 | 109 / 401 |
| 변동계수 | 0.169 |

마지막 청크를 제외하고 모두 정확히 512글자다.

### 확인된 한계

청크1 끝과 청크2 시작:

...시오. 김 대리 좀 들어와 보라고 해. [진양
저수지 의문의 물고기 폐사] 어떡할까요? 관...

대괄호로 묶인 제목이 `[진양` / `저수지`로 분리되었다.
문장 경계를 무시한 결과다.


## 4. 의미 기반 분할

### 알고리즘

문장 분리 → 임베딩 → 코사인 유사도 → 임계값 계산 → 경계에서 분할

계산과 분할을 분리하여 유사도 리스트를 재사용할 수 있게 했다.
시각화와 어블레이션에서 임베딩을 다시 돌리지 않아도 된다.

### 문장 분리

정규식 `(?<=[.!?])\s+|\n+`로 구두점 뒤와 줄바꿈에서 자른다.
lookbehind를 써서 구두점은 앞 문장에 남긴다.
max_length를 넘는 조각은 단어 단위로 추가 분할한다.
(자막은 구두점이 부족해 이 처리가 없으면 조각 하나가 수천 글자가 된다)

### 임계값 방식

- fixed: 지정값 그대로
- percentile: 유사도 하위 amount% 지점
- std: 평균 - amount x 표준편차

### 결과 (부산행.srt, percentile, amount=10)

| 지표 | 값 |
|---|---|
| 문장 수 | 437 |
| 유사도 쌍 | 436 |
| 평균 유사도 | 0.541 |
| 최소 / 최대 | 0.278 / 1.000 |
| 임계값 | 0.404 |
| 자른 횟수 | 44 / 436 = 10.1% |
| 청크 수 | 45 |
| 평균 토큰 | 150.4 |
| 최소/최대 토큰 | 3 / 912 |
| 변동계수 | 1.056 |

설정한 10%와 실제 10.1%가 일치해 percentile이 의도대로
동작함을 확인했다. 완전히 일치하지 않는 것은 percentile이
보간으로 계산되고 `<` 비교가 동점을 처리하기 때문이다.

최대 유사도가 1.000인 것은 동일한 문장이 연속하기 때문이다.
자막에 반복 대사가 존재한다.

## 5. 첫 지표 비교

| 지표 | 단순 분할 | 의미 분할 |
|---|---|---|
| 청크 수 | 19 | 45 |
| 평균 토큰 | 356.5 | 150.4 |
| 최소 토큰 | 109 | 3 |
| 최대 토큰 | 401 | 912 |
| 변동계수 | 0.169 | 1.056 |

### 해석

단순 분할은 크기가 균등하지만 문장이 중간에서 잘린다.
의미 분할은 문장이 온전하지만 크기 편차가 6배 이상 크다.

3토큰짜리 청크("아니.")는 LLM에 넣어도 요약할 내용이 없고,
912토큰 청크는 다른 청크의 6배다. 이 편차가 로드 밸런싱의 대상이다.

토큰/글자 비는 약 0.73으로, 글자 수로 토큰을 추정할 수 없음을
확인했다. LLM 한도 관리에는 토크나이저를 통한 정확한 카운팅이
필요하다.

## 7. top-k 청크 검색

### 목적

청크 수, 토큰 분포, 변동계수는 청킹 결과의 "형태"만 보여준다.
어느 방식이 실제로 유용한지는 판단할 수 없다.

top-k 검색을 붙이면 "질문에 대한 답을 담은 청크를 찾아내는가"라는
기능적 지표를 얻을 수 있다.

### 방식

질문 임베딩 → 모든 청크와 코사인 유사도 → 상위 k개 선택

청킹에서 쓴 것과 같은 코사인 유사도를 쓰되 비교 대상이
"인접 문장 간"에서 "질문 vs 전체 청크"로 바뀐다.

### 동작 확인

혼합 코퍼스(서로 무관한 주제의 문단들로 구성)에 대해
"과거제도는 어떻게 나뉘었나?"로 검색한 결과.

| | 1위 청크 내용 | 유사도 |
|---|---|---|
| 단순 분할(512) | 물 분자의 산소 동위원소 비율 | 0.493 |
| 의미 분할(p10) | "시험은 크게 셋으로 나뉘었다. 문과는... 무과는... 잡과는..." | 0.487 |

단순 분할은 512글자 경계로 자르는 과정에서 과거제도 설명이
여러 청크에 걸쳐 쪼개졌고, 각 청크에 무관한 주제가 섞여
질문과의 유사도가 희석되었다. 상위 3개 모두 관련 없는 내용이었다.

의미 분할은 해당 주제를 온전한 하나의 청크로 유지해
질문에 대응하는 청크를 1위로 검색했다.

주목할 점은 유사도 점수가 0.493 대 0.487로 거의 같다는 것이다.
점수의 절대값만으로는 검색 품질을 판단할 수 없으며,
정답 포함 여부로 평가해야 하는 근거가 된다.

## 8. 트러블슈팅

### 8.1 CUDA 커널 미지원

RuntimeError: CUDA error: no kernel image is available for execution
NVIDIA GeForce RTX 3090 with CUDA capability sm_86 is not compatible
The current PyTorch install supports sm_37 sm_50 sm_60 sm_70

서버의 torch 1.12.1이 CUDA 10.2 빌드라 RTX 3090(sm_86)을
지원하지 않았다. nvidia-smi가 표시하는 CUDA 11.6은 드라이버가
지원하는 최대 버전이지 torch 빌드 버전이 아니다.

대응: 시스템 패키지를 건드리지 않기 위해 프로젝트 전용 가상환경을
만들고 cu118 빌드를 설치했다.
`torch.cuda.get_arch_list()`에 sm_86이 포함됨을 확인했다.


### 8.2 Python 3.11 환경 구축

Qwen3 계열은 transformers 4.51+를 요구하고, 이는 Python 3.9+가
필요하다. 서버 시스템 Python은 3.8이며 venv는 인터프리터를
시스템에서 심볼릭 링크로 참조하므로 버전 문제가 해결되지 않는다.

conda는 Python 인터프리터를 직접 설치하지만, 서버 방화벽이
repo.anaconda.com을 차단해 패키지 메타데이터를 받지 못했다.

CondaHTTPError: HTTP 000 CONNECTION FAILED for url
https://repo.anaconda.com/pkgs/main/linux-64/repodata.json

uv는 Python을 GitHub에서, 패키지는 PyPI에서 받으므로 차단된
경로를 타지 않는다. PyPI는 기존 pip 설치가 성공한 것으로
접근이 확인되어 uv로 전환했다.

uv venv --python 3.11 .venv311
uv pip install torch --index-url https://download.pytorch.org/whl/cu118

torch 2.7.1+cu118, transformers 5.16.1이 설치되었고
Qwen3-4B와 Qwen3-Embedding-4B 로드를 확인했다.

### 8.3 환경 변경 후 재현 확인

Python 3.11 환경 구축 후 동일 스크립트를 재실행해 측정값이
그대로 재현됨을 확인했다.

| 항목 | Python 3.8 환경 | Python 3.11 환경 |
|---|---|---|
| 평균 유사도 | 0.541 | 0.541 |
| 임계값 | 0.404 | 0.404 |
| 자른 횟수 | 44 / 436 | 44 / 436 |
| 청크 수 | 45 | 45 |
| 변동계수 | 1.056 | 1.056 |

torch 2.4.1 → 2.7.1, transformers 4.46.3 → 5.16.1로 변경했음에도
소수점 셋째 자리까지 동일하며, 코드 수정 없이 그대로 동작했다.

### 8.4 잘게 쪼개진 청크

amount=20에서 88개 청크가 생성되었고 2~3토큰짜리가 다수 포함되었다.
amount를 10으로 낮춰 45개로 조정했다. 근본 해결은 min_chunk_size
도입이며 로드 밸런싱과 함께 구현한다.
